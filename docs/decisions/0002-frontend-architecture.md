# 0002. Архитектура фронтенда: Feature-Sliced Design

- Статус: Принято
- Дата: 2026-10-26

## Контекст

Клиент будет расти от одного сценария до нескольких платформ, и в нём будут работать несколько человек и ИИ-ассистенты. Нужна структура, в которой понятно, куда класть код, и которая не даёт модулям срастаться.

## Решение

[Feature-Sliced Design](https://feature-sliced.design/ru/) в `apps/web/src`:

| Слой       | Что лежит                                         | Пример                     |
| ---------- | ------------------------------------------------- | -------------------------- |
| `app`      | Точка входа, провайдеры, роутер, глобальные стили | `app/router`               |
| `pages`    | Экраны, собранные из виджетов и фич               | `pages/home`               |
| `widgets`  | Крупные самостоятельные блоки экрана              | `widgets/places-map`       |
| `features` | Действия пользователя с бизнес-ценностью          | `features/share-shortlist` |
| `entities` | Бизнес-сущности: данные, запросы, отображение     | `entities/place`           |
| `shared`   | Переиспользуемая инфраструктура без бизнес-логики | `shared/api`, `shared/ui`  |

- Слой импортирует только нижележащие слои. Слайсы одного слоя друг друга не импортируют.
- Каждый слайс отдаёт наружу только `index.ts`. Снаружи импорт через алиас `@/`, относительные пути только внутри слайса.
- Сегменты по назначению: `ui`, `api`, `model`, `lib`, `config`.
- Проверки: Steiger (`pnpm lint:fsd`) и правило ESLint против относительных импортов наружу.
- Правило Steiger `fsd/insignificant-slice` выключено, пока экранов меньше трёх: иначе оно требует сливать сущности в единственную страницу, которая их использует.

## Последствия

- Новичку и ассистенту достаточно ответить «это сущность, фича или виджет», чтобы найти место для кода.
- Чуть больше файлов `index.ts` и папок, чем в плоской структуре.

# Как работаем

## Ветки и PR

- `main` всегда зелёный и готов к выкладке. Прямые пуши запрещены, только PR.
- Ветка на задачу от свежего `main`: `feat/share-shortlist`, `fix/map-zoom`, `chore/deps`.
- PR небольшой (до ~400 строк без лок-файлов), одна логическая задача. Описание по шаблону, ссылка на задачу.
- Мержим squash-ом после зелёного CI и одного ревью. Заголовок PR становится коммитом в `main`, поэтому он тоже в формате Conventional Commits.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/), описание по-русски, проверяет `commitlint` в хуке:

```
feat(web): добавить карту сохранённых мест
fix(api): вернуть 404 для несуществующей подборки
chore(deps): обновить vite
```

Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`, `ci`, `build`, `revert`. Скоупы: `web`, `api`, `core`, `ci`, `deps`, `docs`, `repo`.

## Код

- Форматирование и линт автоматически: Prettier, ESLint и Ruff запускаются на `pre-commit` через lefthook. Не отключайте правила точечно без причины в описании PR.
- TypeScript strict, без `any` и `as` для обхода типов. Данные снаружи (API, env, localStorage) валидируем Zod-схемами.
- Фронтенд по FSD: слои `app → pages → widgets → features → entities → shared`, импорт только вниз и только через публичный API слайса (`index.ts`). Проверяет Steiger и ESLint. Подробнее: [ADR 0002](docs/decisions/0002-frontend-architecture.md).
- Имена файлов в `kebab-case`, компоненты `PascalCase`, хуки `useSomething`.
- Комментарии только там, где код не может объяснить «почему». Мёртвый код, `console.log` и закомментированные блоки не коммитим.
- Новая логика идёт с тестом: юнит-тест рядом с файлом (`*.test.ts(x)`), для API в `apps/api/tests`.
- Тексты интерфейса по-русски: короткий заголовок и одна строка пояснения.

## Безопасность

- Секреты только в `.env` (в `.gitignore`), в репо `.env.example` без значений. CI ищет утёкшие секреты gitleaks-ом.
- Персональные данные из опросов и интервью в репо не кладём.
- Зависимости обновляет Dependabot раз в неделю. Новую зависимость добавляем, только если без неё никак, и пишем зачем в PR.
- Решения, которые трудно откатить, оформляем ADR в `docs/decisions/`.
